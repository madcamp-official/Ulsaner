# 설계 문서 재검토 Q&A (2026-07-24)

> 대상 문서: [`2026-07-23-vuln-injection-training-engine-design.md`](superpowers/specs/2026-07-23-vuln-injection-training-engine-design.md)
> 목적: 브레인스토밍 중 나온 질문·의문을 팀원과 공유하기 위한 정리. 답변은 AI(Claude)와의 논의 내용.

## 배경

기존 설계 문서 + 구현 계획(`docs/superpowers/`)이 이미 AI 브레인스토밍 세션을 통해 작성돼 있던 상태에서, 이번 세션은 그 문서를 처음부터 다시 비판적으로 검토하며 진행했다. 검토자(A 파트=엔진/AST/슬롯 담당)는 백엔드/인프라·클라우드 쪽을 지향하지만 아직 주니어라 이번 프로젝트에서 여러 단계를 찍먹해보고 싶다는 입장.

## 1. AST 변환이 뭔가?

AST(Abstract Syntax Tree)는 소스코드를 텍스트가 아니라 구조화된 트리로 표현한 것. "AST 변환"은 이 트리의 노드를 프로그램적으로 찾아 추가·삭제·교체하는 것.

예시: 아래 코드에서

```python
def get_note(note_id: int, user: User):
    note = db.get(note_id)
    if note.owner_id != user.id:
        raise HTTPException(403)
    return note
```

`if note.owner_id != user.id: raise ...` 노드 자체를 트리에서 삭제하면 IDOR 취약점이 주입된 버전이 됨. 문자열 치환이 아니라 트리 조작이라서 안전하고 정확하게 할 수 있음(아래 3번 참고). `libcst`는 이런 조작을 하면서 원본 포맷(주석, 공백)을 보존해주는 파이썬 라이브러리.

## 2. 이 프로젝트에서 AST는 정확히 어디에 쓰이나?

파이프라인 중:
1. **슬롯 라이브러리** — 미리 검증된 취약 코드 조각 준비 (AST 불필요)
2. **주입 엔진 ← AST 사용 지점** — 템플릿 앱을 `libcst`로 파싱 → 타깃 함수 노드를 슬롯의 취약 버전으로 교체, 하드 티어는 주변 코드까지 재배열
3. **레퍼런스 익스플로잇 생성** — 변형 후 실제 필드명/경로를 AST에서 추출해 그 인스턴스에 맞는 익스플로잇 생성

## 3. 문자열 치환 대비 AST의 장점은?

1. **항상 문법적으로 유효한 코드가 나옴** — 문자열 치환은 들여쓰기 등이 깨져 `SyntaxError` 위험 있음
2. **정확한 위치만 타깃팅** — 텍스트 패턴은 앱 다른 곳에도 우연히 매칭될 수 있음. AST는 트리 상의 정확한 문맥(예: "get_note 함수 안의 이 노드")으로 지정
3. **(libcst 한정) 포맷·주석 보존** — 취약점 주입된 함수만 스타일이 튀지 않음
4. **안전한 재배열 가능** — 문장 순서를 바꾸려면 데이터 의존성을 알아야 하는데, 이건 트리 구조에서만 판단 가능
5. **Semgrep 자체가 AST 기반 매칭 도구라서**, 텍스트 표면이 아니라 구조 자체를 흔들어야 실제로 탐지를 회피함

## 4. 인턴 포트폴리오 자료로서 면접관이 관심 가질 만한가?

**결론: 그렇다, 조건부로.** CRUD/클론 프로젝트가 많은 인턴 포트폴리오 중에서 눈에 띄는 항목이라 "이건 뭐지?"가 자연스러운 첫 질문이 되고, 이어서 아래 딥다이브로 이어질 가능성이 큼:

1. "왜 문자열 치환이 아니라 AST로 했나?" — 정답성/견고함 이해도 확인
2. "생성된 앱이 항상 풀린다는 걸 어떻게 보장하나?" (자가검증 루프) — 신뢰성/테스트 철학
3. "취약한 코드를 어떻게 안전하게 격리 실행하나?" (Docker, non-root, 네트워크 차단) — 시스템 설계
4. "AI 감사기가 뚫으면 어떻게 하나?" (적대적 루프, 성공률 측정) — 실험/측정 방법론

**단, 준비 안 하면 역효과 나는 지점**:
- 1번 질문에 "주변 코드를 재배열한다"는 개념 수준 답만 있으면 뭉툭해 보임 → 구체적 알고리즘화 필요 (→ 6, 7번 논의로 이어짐)
- 4번은 실제 숫자(VibeCutter X% vs 사람 Y%)가 있어야 설득력 있음
- 코드에 결함을 주입한다는 컨셉은 "뮤테이션 테스팅"(PIT, Stryker 등, 테스트 품질 측정용으로 버그를 주입하는 기법)과 인접 — 미리 알고 있으면 novelty 주장을 더 정교하게 방어 가능

## 5. 설계 방향 비판적 검토 — 의의 / AI 의존도 / 설계 단계 AI 관여

**구조적 사실:** `docs/superpowers/specs/...`, `docs/superpowers/plans/...`라는 경로는 `superpowers:brainstorming`/`writing-plans` 스킬이 스스로 정하는 저장 규칙과 정확히 일치. 즉 이 설계 문서·계획은 **이전 세션에서 이미 AI 브레인스토밍을 거쳐 나온 산출물**일 가능성이 매우 높음 (커밋 타임스탬프상 두 문서가 같은 초에 커밋됨 = 한 세션에서 이어서 진행 후 한꺼번에 커밋).

- **문제는 "AI를 썼냐"가 아니라 "AI가 제안한 걸 실제로 이해하고 동의해서 골랐냐"**. 자가진단: 문서 안 보고 "왜 하이브리드 주입방식(순수 AST도 순수 슬롯도 아닌)을 골랐는지", "왜 flag 기반 검증으로 통일했는지", "왜 easy 티어를 대조군으로 남겼는지" 막힘없이 설명 가능한지 확인해볼 것.
- **의의(novelty) 문구 재검토 필요**: "교육용 취약 앱 절차 생성 제품은 현재 없다"(섹션 2)는 과장 위험. 보안연구 쪽엔 소스에 자동으로 취약점을 주입하는 선행연구(예: LAVA류)가 이미 존재함(사람 훈련용은 아니지만). → "자동 취약점 주입 자체는 선례가 있지만, 사람 훈련 + AI 감사기 저항성을 목표로 한 조합은 흔치 않다"는 식으로 주장을 좁히는 게 더 방어 가능함.
- **전체 의의**: "시장에 없는 제품"이라는 스타트업식 포지셔닝보다, "일주일 안에 AST 조작·컨테이너 격리·검증 파이프라인·벤치마킹까지 엮어낸 판단력+실행력 증거"로 포지셔닝하는 게 인턴 면접에서 더 설득력 있음.

## 6. "AI가 제안한 걸 이해하고 동의해서 골랐다"를 어떻게 어필하나?

제안한 4단 구조("어느 단계에서 / AI가 어떤 대안을 제안했고 / 각 방안의 장단점을 어떻게 이해했고 / 그래서 뭘 선택했는지")는 **필요하지만 충분하지 않음** — AI가 만든 비교표를 암송하는 것과 구분이 안 될 수 있음. 추가로 필요한 것:

1. **AI가 제시한 기준이 아니라 본인만의 기준으로 재구성해서 설명** (예: "AI는 신뢰성 vs 깊이로 나눴지만, 나한텐 3일차 리스크 게이트가 결정적이었다")
2. **AI 제안을 그대로 안 받고 실제로 수정/반박한 지점이 최소 하나 있어야 함** — 이번 세션에서 실제로 생긴 사례: (a) novelty 주장을 그대로 안 받아들이고 좁힌 것, (b) A/B 역할 분담에서 자가검증-Docker 다리를 추가하기로 조정한 것
3. **반론에 버틸 수 있어야 함** — "참신함을 포기하고 왜 신뢰성을 택했나?" 같은 역질문에 문서를 다시 읽는 수준이 아니라 자기 논리로 답할 수 있어야 함

## 7. "AI가 못 푼다"의 근거를 난이도로 두는 게 이상하지 않나? → 논의 후 도출된 결론

**제기된 문제**: "난이도가 높아서 AI가 못 푼다"는 결과를 원인처럼 말하는 순환논리이자, 두 가지 다른 실패 메커니즘을 뭉뚱그림:
- Semgrep(정적 패턴 매칭)이 실패하는 이유(고정 패턴 없음)와
- Claude 기반 VibeCutter가 실패하는 이유는 다름 — LLM은 패턴이 아니라 의미로 추론하므로, 변수명/문장순서 재배열이 Semgrep은 속여도 Claude의 의미 추론까지 속일 이유는 약함. 실제로 문서 섹션 14는 "Claude는 추론으로 로직 결함도 풀 수 있음"이라 인정하고 있어 섹션 2/8의 "AI가 못 푸는 지점"이라는 주장과 내부 모순.
- 또한 "지금 이 모델 기준 어렵다"는 주장은 모델이 좋아지면 무너지는 유효기간 있는 주장.

**추가 질문**: 코드만으로 답이 결정 안 된다면, AI(그리고 사람)는 대체 뭘 보고 판단하나?
→ 확인 결과: 학생과 AI 둘 다 (1)소스 코드 (2)`manifest.json`의 `task_prompt`(의도가 이미 평문으로 명시됨, 예: "다른 사용자의 비공개 데이터를 읽어라") (3)실행 중인 앱을 찔러본 반응을 동일하게 봄. **즉 "의도가 숨겨져 있다"는 초기 설명은 틀렸음** — task_prompt에 의도가 이미 나와 있고, 안 그러면애초에 "반드시 풀린다"는 자가검증 요구사항(섹션 6-5) 자체가 성립 불가.

**최종 정리된 진짜 메커니즘**: "난이도"도 "숨겨진 의도"도 아니라, **"권한 체크의 존재(existence) 판단 vs 그 체크의 정확성(correctness) 판단"의 차이**.
- easy/idor: 체크가 **아예 없음** → "있냐 없냐"만 보면 됨. 패턴매칭도 LLM도 잘함.
- hard/idor: 체크가 **있긴 있음**(예: `team_id == user.team_id`) 하지만 이 인스턴스의 실제 데이터 모델에서 진짜 소유권과 동치가 아닌 필드를 비교함 → "체크가 있으니 안전"이라 오판하기 쉬움. 게다가 어떤 필드가 진짜 소유권인지는 인스턴스마다 랜덤이라 "owner_id면 안전"같은 암기된 휴리스틱이 매번 안 통함.
- 이건 실제 AppSec에서도 구분되는 버그 클래스(missing authorization vs broken/insufficient authorization)이고, 정보를 숨기지 않고도(소스·task_prompt 다 공개) 왜 성공률이 구조적으로 낮게 나오는지 설명 가능 → 섹션 2/8/14의 모순도 해소됨.
