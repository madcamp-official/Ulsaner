# 취약점 주입 훈련 엔진 — 설계 문서

> 몰입캠프 4주차 자유주제 · 2인 · 일주일 · 작성일 2026-07-23
> 프로젝트: Ulsaner (github.com/madcamp-official/Ulsaner) · 몰입캠프 26s-w4-c2-03

## 1. 개요 (Thesis)

**정답을 찾아볼 수 없는, 매번 새로 생성되는 웹 취약점 훈련 엔진** — LLM 시대에도 외운 답이 아니라 '실제로 풀어야' 통과하는 연습장.

PortSwigger·WebGoat·bWAPP 같은 기존 해킹 학습 랩은 문제가 **손으로 만든 고정된 것**이라 두 가지 문제가 있다.

1. 정답이 인터넷·LLM 학습데이터에 있어 **ChatGPT에 붙여넣으면 풀린다** (연습이 안 됨).
2. 문제가 유한하고 모두가 같은 문제를 본다 (치팅·재사용).

이 엔진은 템플릿 앱의 코드를 **자동 변형(AST 조작)**해 취약점을 매번 다른 위치·형태로 심고, 격리 배포하고, 익스플로잇을 자동 검증한다. 학생마다 **유니크한 취약 앱**을 받으므로 암기 정답이 통하지 않는다.

**핵심 thesis(2026-07-24 정정 — "AI가 못 푼다"는 순환논리·유효기간 있는 주장이라 폐기):**

1. **"AI가 못 푼다"가 아니라 "정답을 찾아볼 수 없다".** 문제가 매번 새로 생성돼 어떤 학습데이터·기존 풀이에도 없으므로, LLM을 쓰든 안 쓰든 **외운 답을 꺼낼 수 없고 매번 실제로 추론**해야 한다(암기 무력화 = 학습 무결성). 강해진 모델도 '처음 보는' 인스턴스는 기억에서 못 꺼내고 실제로 풀어야 하며 — 학습 도구 관점에선 AI가 '정답 열쇠'에서 '추론 파트너'로 바뀔 뿐 의의가 깨지지 않는다.
2. **자동 보안도구엔 '못 푼다'고 주장하지 않고 "측정"한다.** 정적 벤치마크는 학습데이터에 오염돼 진짜 능력을 못 잰다(benchmark contamination). 절차 생성은 **오염되지 않은 신선한 인스턴스를 무한 공급**해, 자동도구(옆 분반 VibeCutter: Semgrep+Playwright+Claude)의 성공률을 시간에 걸쳐 유효하게 잰다. 모델이 좋아지면 벤치마크가 그 향상을 수치로 보여줄 뿐 — 여전히 유용.

두 축 모두 **모델 발전과 무관하게 유효**하다. (교과서 취약점 대신 **비즈니스 로직/접근제어 결함**에 집중하는 이유는 §8 참고 — 정적분석은 확실히 이기지만 LLM 추론엔 면역을 주장하지 않는다.)

## 2. 목표 & 성공 기준

- **주 목표:** 인스턴스마다 유니크한, 반드시 풀리는 취약 앱을 자동 생성·배포·검증하는 end-to-end 시스템.
- **차별화(novelty), 3층 구조:**
  1. **(핵심, 최우선) 인스턴스 유니크성** — PortSwigger·WebGoat·bWAPP는 물론 TryHackMe·HackTheBox 같은 인스턴스 격리형 플랫폼도 취약점 자체는 모든 유저에게 동일하다. 이 프로젝트는 AST 변형으로 위치·필드명·구조가 인스턴스마다 달라져 write-up/암기 정답이 무력화된다. (자동 취약점 주입 자체는 보안연구에 선례가 있으므로, novelty는 "사람 훈련 + AI 감사기 저항성을 함께 겨냥한 조합은 흔치 않다"는 수준으로 한정한다.)
  2. **콘텐츠 전략 — 접근제어/로직 결함 심화**: 기존 플랫폼은 교과서 취약점(SQLi·XSS 등) 위주로 폭넓고 얕게 다룬다. OWASP Top 10 1위인 Broken Access Control은 고정 패턴이 없어 정적분석·자동화로 못 잡고 가르치기도 어려워 상대적으로 덜 다뤄진다 — 이 카테고리를 깊게 판다.
  3. **증거 레이어 — 실증된 저항성 + 자동 품질보증**: 필드명에 무관한(메타변수 기반) Semgrep 규칙 하나로 "권한 체크 존재(missing) vs 정확성(broken)" 차이를 실제로 증명한다 — easy/idor는 걸리고 hard/idor는 안 걸림을 실제 semgrep 실행으로 확인(구현·검증 완료). 자가검증 루프로 생성물이 늘어나도 품질(항상 풀림)이 자동으로 보장된다 — 손으로 만드는 플랫폼은 콘텐츠가 늘수록 수동 QA 부담이 커진다. (VibeCutter 성공률 비교는 구현 중 VibeCutter가 배치 실행 가능한 CLI가 아니라 다단계 승인이 필요한 MCP 서버임이 밝혀져 스트레치로 이동 — 섹션 14 참고.)
- **성공 기준:**
  - (바닥) `easy/idor` 챌린지가 생성→배포→익스플로잇→검증까지 E2E로 동작. **(달성)**
  - (핵심) `hard/idor`가 "권한 체크는 있으나 이 인스턴스의 실제 소유권 관계에선 틀린 필드/스코프를 비교"하도록 설계되어, 필드명 무관 Semgrep 규칙으로 안 잡힘을 실증. **(달성)** VibeCutter 성공률 비교(당초 목표)는 인터페이스 문제로 미달성 — 스트레치.
  - (발표) "체크 존재 여부만 보면 안전해 보이지만 실제로는 취약하다"를 Semgrep 실행 데이터로 라이브 시연.

## 3. 범위 & 비범위

**범위 (MVP)**
- 템플릿 FastAPI 앱 1개.
- 취약점 2종 × 난이도 2티어: `easy/idor`, `easy/sqli`, `hard/idor` (하드 SQLi는 스트레치).
- 하이브리드 주입(파라미터화 슬롯 + AST 배치/재배열).
- 인스턴스당 Docker 격리 배포.
- flag 기반 검증.
- 기본 웹 UI + VibeCutter 벤치마크 지표.

**비범위 (YAGNI)**
- 플랫폼 회원가입/인증 (인스턴스 세션 토큰으로 대체).
- 리더보드, 영속 저장, 프로덕션급 오케스트레이션(k8s 등).
- 게이미피케이션(포인트·뱃지·랭킹) — MVP 비범위. 단, 검증 서비스의 시도/결과 로깅에 `user_id`·`challenge_id`·시도 이력 필드 여유를 둬서 나중에 얹기 쉽게만 해둔다(섹션 17 참고).
- LLM 에이전트 vs 사람 라이브 자동화(스트레치, 없으면 수동/녹화 데모).

## 4. 아키텍처

두 덩어리를 **챌린지 번들**이라는 단일 계약이 연결한다.

```
[엔진 · 사람 A]                         [플랫폼 · 사람 B]
templates/ (깨끗한 앱)
engine/
  - 취약 슬롯 라이브러리
  - 주입 엔진(슬롯선택 + AST 배치/재배열)   ── 챌린지 번들 ──▶  orchestrator/
  - 레퍼런스 익스플로잇 생성                                    - 번들을 Docker로 격리 배포
  - 자가검증(생성물이 실제로 뚫리는지)                          - 인스턴스 URL 발급 + 수명주기
  - VibeCutter 벤치마크 하네스                                platform/
                                                              - 검증 서비스(flag 판정)
                                                              - 웹 UI + 대시보드 + 데모
```

## 5. 핵심 계약: 챌린지 번들 & manifest 스키마

번들 = 하나의 디렉토리.
- `app/` — 변형된 FastAPI 앱 소스 (+ `Dockerfile`)
- `manifest.json` — 메타데이터

```json
{
  "id": "uuid",
  "vuln_type": "idor | sqli",
  "tier": "easy | hard",
  "entry": { "port": 8000, "task_prompt": "다른 사용자의 비공개 데이터를 읽어 flag를 찾아라" },
  "flag": "FLAG{...}",
  "verify": { "method": "flag_submit" },
  "_internal": {
    "flag_planted_in": "user 42의 비공개 노트",
    "reference_exploit": "exploits/idor_a1b2.py",
    "solution_summary": "..."
  }
}
```

- 학생에게는 `app/`(실행 앱)만 노출(블랙박스). `flag`·`_internal`은 플랫폼이 검증용으로만 보유.
- `manifest_schema.json`(`contract/`)이 **유일한 공용 파일** — 1일차에 합의, 수정 전 서로 공지.

## 6. 컴포넌트

**엔진 (사람 A) — `engine/`, `templates/`**
1. 템플릿 앱 — 멀티유저 FastAPI(유저, 소유자 있는 리소스, 비공개 데이터).
2. 취약 슬롯 라이브러리 — (종류 × 티어)별 미리 검증된 변형. `easy/idor`(소유권 체크 누락), `easy/sqli`(문자열 이어붙이기), `hard/idor`(틀린 소유권 필드 / 스코프 혼동 / 다단계 로직 결함).
3. 주입 엔진 — 시드 → 슬롯+파라미터(타깃 리소스, flag 비밀값, id 체계) → 취약 변형 렌더 → AST로 랜덤 위치 배치 + 주변 재배열(이름/순서/래핑).
4. 레퍼런스 익스플로잇 생성 — 슬롯+파라미터에서 도출한 정답 익스플로잇(자가검증·벤치마크용, 학생 노출 X).
5. **자가검증** — 갓 생성한 인스턴스에 레퍼런스 익스플로잇을 실제로 돌려 flag 도달 확인. 통과분만 출하 → "항상 풀린다" 보장 + AST 변형이 앱을 깨거나 못 뚫게 만들 위험 차단.
6. 매니페스트 출력.
7. VibeCutter 벤치마크 하네스 — 하드 티어에 VibeCutter(화이트박스) 실행, 성공/실패 기록, 슬롯 강화 피드백.

**플랫폼 (사람 B) — `platform/`, `orchestrator/`**
8. 오케스트레이터 — 번들을 격리 Docker로 빌드+실행, URL 발급, 수명주기(TTL·teardown·포트·동시 상한).
9. 검증 서비스 — flag 제출 → manifest와 비교 → 통과/실패, 시도 로깅.
10. 웹 UI + 대시보드 — 챌린지 선택 → 스핀업 → task_prompt+URL → 제출 → 결과 + VibeCutter vs 사람 통계.

## 7. 데이터 흐름

```
1. 생성:   시드 → 엔진 → [자가검증 통과] → 번들
2. 요청:   학생 요청 → 플랫폼이 번들 배포 → 인스턴스 URL + task_prompt
3. 공략:   학생이 실행앱 공격(블랙박스) → 익스플로잇 → flag 획득 → 제출
4. 판정:   검증 서비스 비교 → 통과 → 인스턴스 teardown
5. 벤치마크(별도): 엔진이 인스턴스 생성 → VibeCutter 화이트박스 실행 → 성공률 기록 → 슬롯 강화
```

## 8. 취약점 클래스 & 티어 전략 (정적분석 저항 + 측정)

- **easy 티어(대조군):** 권한 체크가 **아예 없음**(missing authorization). "체크의 존재 여부"만 판단하면 되므로 Semgrep도 잡고 VibeCutter도 푼다. "존재 여부 판단은 AI도 쉽다"의 대비군.
- **hard 티어(주력):** 권한 체크가 **존재는 하지만 틀린 필드/스코프를 비교**함(broken/insufficient authorization — 예: 진짜 소유권 필드 대신 `team_id` 같은 유사 필드를 비교). "체크가 있으니 안전하다"는 얕은 판단으로는 못 잡고, 이 인스턴스의 실제 엔티티 관계를 정확히 추적해야만 발견 가능하다. 어떤 필드가 진짜 소유권인지는 인스턴스마다 랜덤이라 암기된 휴리스틱("owner_id 비교면 안전")이 매번 안 통한다. AST 재배열은 여기에 더해 Semgrep 같은 패턴 매칭의 고정된 모양까지 없앤다.
- **핵심 통찰:** 차별점은 "난이도가 높다"가 아니라 **"체크의 존재(existence) 판단과 체크의 정확성(correctness) 판단은 전혀 다른 종류의 작업"**이라는 것이다. 존재 판단은 패턴매칭·LLM 둘 다 쉽고, 정확성 판단은 인스턴스별 데이터 모델을 매번 새로 정확히 추적해야 해서 소스·task_prompt를 전부 공개해도(화이트박스) 구조적으로 놓치기 쉽다. 이건 모델이 발전해도 쉽게 안 없어지는 차이이며, Claude 기반 VibeCutter가 "추론으로 로직 결함을 풀 수도 있다"는 사실과도 모순되지 않는다(섹션 14 참고).

## 9. 주입 메커니즘 (하이브리드, 접근법 C)

- **파라미터화 슬롯(신뢰성 backbone):** 미리 검증된 취약 변형을 선택하고 위치·필드·비밀값을 시드로 랜덤화 → 항상 익스플로잇 가능.
- **AST 배치/재배열(하드 코어):** libcst로 취약 변형을 큰 앱의 랜덤 위치에 심고 주변 코드를 재배열 → 진짜 유니크함 + Semgrep 패턴/LLM 위치추론 교란.
- 순수 AST 자유 변형(A안)은 "항상 익스플로잇 가능"을 보장 못 해 일주일엔 위험하여 배제. 순수 슬롯(B안)은 AST 깊이가 약해 배제.

## 10. 검증 설계 (flag 기반)

- 인스턴스마다 유니크한 비밀값(flag)을 **익스플로잇해야만 도달하는 리소스**(예: 다른 유저의 비공개 데이터)에 심는다.
- 학생은 취약점을 실제로 공략해 flag를 읽고 제출 → 문자열 비교로 판정.
- IDOR·SQLi 양쪽에 동일하게 통해 검증을 단순화. (선택: 서버측 비인가 접근 로깅을 2차 신호로.)

## 11. 격리 / 딜리버리

- 인스턴스당 Docker 컨테이너(하드 티어는 코드가 인스턴스마다 다름).
- 자원 상한, 네트워크 격리(아웃바운드 차단·자기 DB만), non-root, 가능시 read-only rootfs.
- 수명주기: TTL 자동 teardown + 풀면 teardown + 동시 인스턴스 상한.
- 포트: 인스턴스마다 **동적 포트 할당**(MVP — 플랫폼이 포트를 추적). 리버스 프록시 경로 라우팅은 향후 확장. 베이스 이미지 미리 빌드해 스핀업 단축.

## 12. 에러 처리

- **엔진:** 생성/자가검증 실패 → 폐기 후 새 시드로 재생성(횟수 제한), 실패 슬롯/시드 로깅. 자가검증 통과분만 출하.
- **플랫폼:** 컨테이너 빌드/실행 실패 → 1회 재시도 후 에러 표시. 인스턴스 죽음 → 헬스체크 감지 → 재스핀. TTL 청소 + 고아 컨테이너 회수. 동시 상한 초과 → 대기/지연. flag 제출 레이트리밋, TTL 만료 인스턴스 거부.

## 13. 테스트 전략

- **엔진(속성 기반):** 슬롯 × 티어마다 N 시드 → ① 앱 부팅 ② 레퍼런스 익스플로잇 성공(flag 도달) ③ [하드] Semgrep이 안 잡는지 sanity.
- **계약 테스트:** 생성 `manifest.json`이 스키마에 부합.
- **플랫폼 통합:** fixture 번들 → 배포 → 올바른/틀린 flag/TTL 만료 경로.
- **E2E:** 엔진 생성 → 플랫폼 배포 → 라이브 인스턴스에 레퍼런스 익스플로잇 → flag 제출 → 통과. (작동 증명 겸용)
- **핵심 증거(지표, 달성):** Semgrep 규칙 하나로 easy/idor는 플래그되고 hard/idor는 플래그 안 됨을 실제 실행으로 확인 — "체크 존재 vs 정확성" 차별화의 falsifiable한 증명.
- **벤치마크(스트레치, 미달성):** VibeCutter 배치 성공률 = 추적 숫자(발표용 "VibeCutter X% vs 사람 Y%")로 기획했으나, VibeCutter가 배치 CLI가 아니라 다단계 승인형 MCP 서버로 밝혀져 exit-code 기반 하네스로는 측정 불가(섹션 14).

## 14. VibeCutter 벤치마크 & 위협 모델

- **위협 모델:** 학생 = 블랙박스(소스 없이 실행앱 공격, 실전 펜테스트). VibeCutter 벤치마크 = 화이트박스(소스 제공, 정상 모드) → 소스·task_prompt를 다 줘도 "체크의 정확성"까지 매번 놓치지 않고 검증하긴 어렵다는 것을 측정하는 게 목표(섹션 8 참고). "무조건 못 푼다"가 아니라 존재 판단 대비 정확성 판단에서 성공률이 유의미하게 낮아짐을 보이는 것.
- **적대적 개발 루프:** VibeCutter(오픈소스: madcamp-official/VibeCutter)를 직접 돌려 hard 티어가 뚫리면 그 변형은 버리고 슬롯/재배열을 강화. "추측이 아니라 측정."
- **정직한 포지셔닝:** VibeCutter는 Claude 기반이라 로직 결함도 추론으로 풀 수 있다. 목표는 "불가능"이 아니라 "존재 판단 대비 정확성 판단에서의 저항/성공률 저하"이며, 이는 모델이 발전해도 구조적으로 남는 차이라는 게 핵심 주장이다(섹션 8).
- **구현 중 발견 (2026-07-24) & 포지셔닝 조정:** VibeCutter를 실제로 클론·조사한 결과, "타깃 디렉토리 → 성공/실패 exit code"로 배치 실행 가능한 CLI가 아니라, LLM 호스트(Claude)가 ~28개 툴을 단계별 사람 승인 하에 호출하는 MCP(Model Context Protocol) 서버였다. 자체 배치/eval 스크립트도 있지만 VibeCutter 자신의 인벤토리에 사전 등록된 앱(자체 clone)만 대상이 가능하고, 그중 하나는 캠프 내부망 전용 LLM 엔드포인트가 필요해 접근 불가. 이 상태로는 exit-code 기반 벤치마크 하네스로 신뢰할 수 있는 성공률을 뽑을 수 없어, **VibeCutter 성공률 실측은 스트레치로 미루고, 핵심 증거는 Semgrep 규칙(위 항목, 실제 구현·검증 완료)으로 대체한다.** "AI 감사기 대비 저항"이라는 주장 자체는 유지하되, 근거를 "VibeCutter 성공률 수치"에서 "정적분석 기반 자동 탐지(Semgrep)에 대한 실증된 저항"으로 좁힌다 — 발표에서는 VibeCutter 관련 위협모델·포지셔닝은 향후 확장(로드맵)으로 언급하고, 라이브 데모/데이터는 Semgrep 결과 중심으로 한다.

## 15. 일주일 일정 & 2인 분업

**전략: 바닥 먼저, 하드 코어는 그 위에 층으로.**

| 일 | 사람 A (엔진) | 사람 B (플랫폼) |
|---|---|---|
| 1 (같이) | git 골격, `manifest_schema.json` 합의, 템플릿 앱, Docker 베이스 이미지 | (같이) |
| 2 | `easy/idor` 슬롯+주입+레퍼런스 익스플로잇+자가검증 → 첫 번들 | fixture 번들 Docker 배포 → URL, 웹 UI 골격 |
| 3 | `easy/sqli` + `hard/idor` 착수 / **통합·첫 E2E = 바닥 데모** | TTL/teardown, 동시 상한, 검증 견고화, 대시보드 착수 |
| 4 | `hard/idor` 로직결함 + AST 배치/재배열 + Semgrep 테스트(**핵심 증거, 달성**) / VibeCutter 벤치마크는 MCP 서버 구조 문제로 스트레치 이동 | 대시보드 통계, UI 폴리싱 |
| 5 | 견고화·버그·데모 리허설·버퍼 | (같이) |

**분업:** A=`engine/`,`templates/` · B=`platform/`,`orchestrator/` · 공용=`contract/manifest_schema.json`(수정 전 공지). B는 fixture로 선행해 A 없이도 안 막힘.

## 16. 리스크 & 완화

- **3일차 바닥(easy/idor E2E)이 게이트.** 못 넘으면 SQLi·하드티어 컷.
- 하드티어(AST 재배열 + VibeCutter 벤치마크)가 난이도·novelty의 핵심이자 최고 리스크 → 바닥 뒤 층으로 배치. 최악에도 바닥+컨셉 데모 가능. **(리스크 실현됨: VibeCutter가 MCP 서버라 배치 벤치마크 불가로 판명 → Semgrep 실증으로 대체, 컨셉 데모는 그대로 유지)**
- 로직 결함 자동 주입이 교과서보다 까다로움 → 슬롯 라이브러리로 신뢰성 확보, AST는 배치/재배열에 한정.

## 17. 향후 확장 (로드맵)

- 취약점 유형 추가 = "슬롯 규칙 + 검증" 추가(유형당 며칠). 폭은 딜리버리가 아니라 로드맵.
- LLM 에이전트 자동 벤치마크로 난이도 자동 보정.
- 다중 언어 템플릿(Node 등).
- **게이미피케이션**: 포인트·뱃지·랭킹, 슬롯 종류(존재-판단형 vs 정확성-판단형)별 챌린지 스킬트리, "AI가 못 뚫은 인스턴스를 사람이 풀었을 때" 별도 하이라이트/보상. MVP에서 만들진 않지만, 검증 서비스의 시도/결과 로깅 스키마에 `user_id`·`challenge_id`·시도 이력 필드 여유만 지금 단계에서 확보해두면 나중에 얹기 쉬워진다(섹션 3 비범위 참고).
